**Read this as evidence the mechanism works, not as the pitch's headline
number.** This is a single Docker container's default Postgres config
(small shared_buffers, one connection, no tuning) on a laptop, not a
properly resourced target — the absolute millisecond figures below would
not survive being quoted as "the platform's real-world latency." What DOES
survive, and is the actual point of #57's second half:

1. **The InitPlan idiom works as designed.** Every RLS-injected subquery
   (`auth_divisions()`, `my_service_connection_ids()`, etc.) shows up as its
   own `InitPlan N -> Result (... loops=1)` node — computed exactly once per
   query, never once per row. This is true across all three queries below,
   including the one that touches 1.26M rows.
2. **Partition pruning works as designed.** The division-scoped scan's
   `Append` node shows `Subplans Removed: 1` and only touches the two
   partitions that actually could contain matching rows
   (`meter_readings_2026_08`, `meter_readings_2026_09`) via each
   partition's own `_div_idx` — not a scan across every partition in the
   table.
3. **A genuine, honestly-reported caveat: the full-division `count(*)`
   stayed slow (~15.7s) on a *second* run, not just the first.** The
   division-scoped top-100 query dropped from 3.68s (cold) to 2ms (warm) —
   ordinary first-read hint-bit-setting cost after a bulk `INSERT`, as
   expected. The full count did not get faster on a warm rerun
   (`Buffers: ... read=15478` even the second time) — this container's
   `shared_buffers` is too small to hold the ~30k pages this scan touches,
   so it re-reads from OS cache/disk every time. That is a real, measured
   fact about this specific local environment, not about the RLS design or
   the partitioning scheme — a target with `shared_buffers` sized for its
   actual data volume (any real Supabase project tier does this) would not
   show this. Re-run this same script against such a target before quoting
   an absolute latency number in the pitch; the mechanism evidence above
   already stands on its own.
